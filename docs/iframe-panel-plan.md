# 面板 iframe 化方案讨论

面向「粉笔综合工具」油猴脚本的面板 UI 隔离改造。本文记录围绕 iframe 化的讨论结论、目标形态、遗留阻力与建议路线，供后续落地时对照。

## 讨论背景

面板（浮球 + 题目 ID / 课程信息两个折叠区）当前直接以普通 DOM 挂在宿主页面里，样式通过 `GM_addStyle` 全局注入，用 `#fenbi-id-panel` 前缀勉强维持隔离。已经暴露过实际问题：外层容器固定 `max-height` 导致展开多层课程后内容被裁、滚动条滚不到底（已在 `64eba00` 修复）。这类问题说明“与宿主共享样式上下文”是持续的维护负担来源，于是讨论了三种隔离方向：整面板进 Shadow DOM、浮球留宿主而面板主体进 iframe、整体进 iframe。

## 先澄清两个前提

油猴脚本只能在浏览器扩展环境里运行，宿主就是桌面浏览器（Chrome/Firefox/Edge 一类）。之前提到抓包 URL 里的 `ua=cef`、`device_app=webstudent`，那是粉笔页面自带的业务标识，代表页面面向学生端渲染场景，并不表示脚本运行在 CEF/WebView 里；这条不构成 iframe 化的障碍，予以撤回。

旁路捕获 hook 必须 patch 宿主页面的 `fetch`/`XMLHttpRequest`，因此无论 UI 怎么隔离，hook 与捕获缓存都会留在宿主上下文。UI 进 iframe 的真正成本是 UI 与这份宿主状态之间的通信，而不是 hook 本身。

## 目标形态：浮球留宿主，面板主体进 iframe

采用“浮球在宿主、面板主体在 iframe”的混合形态，避免拖拽浮球跨 iframe 边界收不到鼠标事件的问题。宿主只保留三件事：捕获 hook 与状态缓存、可拖拽浮球、最小消息通道；面板的 DOM、样式、滚动、交互全部进一个同源 iframe（`srcdoc` 或 `about:blank`）。

如果后续面板复杂度足够高，这个形态可以平滑过渡到“独立面板应用”，因为消息通道是同一套。

## 面板对宿主上下文的真实依赖盘点

逐项核对后，面板目前依赖宿主上下文的点只有四个：

| 能力 | 现状 | iframe 化后的形态 |
| --- | --- | --- |
| 网络旁路捕获 | hook 宿主 `fetch`/XHR 并把解析结果写入缓存 | 保留在宿主，捕获后向 iframe 推送增量 |
| 捕获缓存读取 | 渲染函数直接读内存 store | 通过消息通道同步快照 / 按需响应 |
| 剪贴板复制 | `GM_setClipboard`（宿主 API），降级 `navigator.clipboard` | 统一走宿主代理，iframe 只发“复制请求” |
| 手动刷新 | 同步重读缓存并渲染 | iframe 发请求 → 宿主回传最新缓存 → iframe 渲染 |

此前作为第五项依赖的“宿主 window 全局内存扫描”（兜底找题目数据）讨论决定删除（代码尚未实施）：hook 在 `document-start` 就安装，正常页面加载流程中捕获必然先于业务请求；唯一漏网场景是脚本中途被更新或启用，提示用户刷新一次页面即可覆盖。删除后，面板与宿主的耦合只剩上表四项，且都收敛到同一条消息通道。

## 消息通道设计（核心工程量）

iframe 与宿主之间需要一条双向消息通道，覆盖三类交互：

| 方向 | 消息 | 触发 | 载荷 |
| --- | --- | --- | --- |
| host → iframe | `snapshot` | iframe 就绪 | 当前题目/课程缓存全量快照 |
| host → iframe | `capture-push` | 每次捕获到新响应 | 题型（quiz/course）、课程 id、原始响应 |
| iframe → host | `request-refresh` | 用户点“重新获取” | 目标面板（题目 / 课程） |
| host → iframe | `refresh-result` | 宿主查缓存后 | 最新快照 |
| iframe → host | `copy` | 用户点复制按钮 | 文本内容 |
| host → iframe | `copy-result` | 复制完成 | 成功与否 |
| iframe → host | `height-changed` | iframe 内容高度变化 | 目标高度 |

时序要点：宿主对 `request-refresh` 与 `copy` 保持串行响应，防止覆盖写；`capture-push` 合并原 `scheduleCourseRefresh` 的 400ms 防抖，避免高频推送触发 iframe 内重复渲染。面板自身的展开/收起状态完全留在 iframe 内，宿主不感知，天然绕开这次“外层高度不同步裁内容”一类问题。

## 遗留阻力

工程上可解，但落地前要逐项确认：

- 宿主 CSP：动态 iframe 受 `frame-src` / `default-src` 约束；若页面加 `sandbox` 属性，必须同时给 `allow-scripts` 与 `allow-same-origin`，否则 iframe 变成不透明源，拿不到宿主与 GM API。fenbi 页面当前未见相关限制，但要以实测为准。
- 剪贴板：GM API 只注入宿主上下文，iframe 内的 `navigator.clipboard` 依赖焦点与权限且不稳定，因此复制统一走宿主代理（即上表 `copy` 消息），不要在 iframe 内直接调用。
- iframe 高度同步：面板内容会动态长高，需要 iframe 内 `ResizeObserver` 测量并回传高度，宿主设置 `iframe.style.height`；动画展开时做节流。
- 焦点与键盘：焦点进入 iframe 后宿主页面失焦，Tab 顺序在 iframe 边界断裂，读屏把 iframe 视为独立文档。常驻小面板可接受，但属于体验降级。
- 回归测试：现有 `tests/course-regress` 基于同上下文假 DOM 运行，iframe 形态需要模拟宿主通信的新测试基建，否则渲染与数据联动失去自动化覆盖。

## 与 Shadow DOM 方案的对照

| 维度 | 整面板 Shadow DOM | 浮球宿主 + 面板 iframe |
| --- | --- | --- |
| 样式隔离 | 强（两边 CSS 互不可见） | 最强（独立 document） |
| 渲染与数据联动 | 不变，直读内存 store | 需要消息通道与快照同步 |
| 宿主 API（剪贴板等） | 不变，原地可用 | 全部改走宿主代理 |
| 交互边界 | 无 | 焦点、Tab、读屏在 iframe 边界断裂 |
| 改动范围 | 集中在挂载与样式注入 | hook 外新增一层通信协议与状态镜像 |
| 测试影响 | 现有假 DOM 回归基本可复用 | 需要新测试基建 |

两条路线在“样式隔离”上的收益几乎一致，iframe 额外换取的是“可以把面板当独立应用开发、随便上框架”，代价是上述通信层与交互边界成本。

## 结论与建议路线

讨论中已形成两项独立于 iframe 形态本身的决策，先单独记录：

- 删除“宿主 window 内存扫描”兜底，改为假定接口请求发生在脚本加载之后：hook 在 `document-start` 安装，正常页面加载流程中捕获必然先于业务请求；找不到捕获缓存时提示用户刷新页面。此决策当前只落在文档里，代码尚未实施。
- iframe 化的目标形态定为“浮球留宿主、面板主体进 iframe”，避免拖拽跨边界问题；该形态只在面板复杂度显著上升后启用。

当前功能量级（题目 ID + 课程信息两个面板）下，先做整面板 Shadow DOM 改造，隔离收益与 iframe 基本持平，而改动量小一个量级，且不动“捕获→读状态→渲染”的同上下文架构。

iframe 混合形态的触发条件暂定为：面板功能显著扩张（出现表单、弹窗、批量操作等成规模交互），或团队明确要按独立应用的方式迭代 UI。届时在 Shadow DOM 版本基础上补消息通道，宿主侧改动可复用。
